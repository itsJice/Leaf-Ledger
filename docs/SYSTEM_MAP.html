FIG 2What happens on one request

There are no cookies and no server sessions. The browser holds a Supabase access token, every call to /api carries it as a Bearer header, and FastAPI checks the signature against Supabase's public keys before any handler runs. The three lanes happen in this order the first time someone opens the app.

FIG 3How a product gets in, and where it goes

Three intake lanes converge on one products table. Dedupe is scoped per supplier because SKUs collide across vendors. Missing fields stay visible as review work rather than being dropped. From there the same rows feed search, favorites, projects, designs, the ornament calculator, jobs and purchase orders.

FIG 4The data model, in two schemas

The core catalog and project tables sit in public. They came with the platform-generated starter and have no CREATE statement in this repo. Numbered SQL files in backend/migrations/ add columns, indexes and a few tables such as clients and project_rooms. The newer operational tables live in an app-owned ll_app schema, and each router creates its own tables with CREATE TABLE IF NOT EXISTS the first time it runs. Arrows point from parent to child.

FIG 5The install schedule loop

A seasonal side-product inside the same repo. A Python pipeline turns the raw Christmas client spreadsheet into a routed crew schedule and a self-contained review page. Because that page embeds client names, addresses and phone numbers, it is pushed straight into Postgres and served only to signed-in staff, never committed and never baked into the image.
